# 모델 선택과 오케스트레이션 유즈케이스

정책: `usage-aware-2026-09-12`. 우선순위는 **명시적 사용자 모델·추론 선택 → 활성 quota 보호 규칙 → 명시적 프로젝트 모델·추론 → 선택 위임 기본값**이다. 일반적인 선택 위임은 프로젝트 고정을 없애지 않으며, 구체적인 현재 사용자 결정으로 바꿀 수 있다. 기본값을 적용할 때 일반 작업은 **Luna/max**, 복잡한 판단은 **Sol/high 제안**, 매우 어려운 분석은 **Astra/high 제안**이다. xhigh는 구체적 필요가 있을 때만 제안한다. Luna/max는 운영자가 선택한 기본값이며 가성비 우위를 실측한 결론은 아니다. 모델 선택을 위임받은 작업 범위에서는 재승인을 반복하지 않되 호스트의 실제 적용을 확인한다.

## 단계 전환의 판단 순서

1. 완료한 설계의 결정·인터페이스·변경 범위·검증 기준을 짧게 정리한다.
2. 다음 작업을 명세 명확성, 다른 작업과의 결합도, 실패 영향으로 평가한다. 파일 개수만으로 난이도를 정하지 않는다.
3. 짧은 작업은 현재 세션에서 한다. 상당한 독립 작업은 Luna/max 작업자로 분리할 수 있다. 긴 순차 작업 하나는 모델 전환이 허용되고 지원될 때 같은 세션에서 전환하되, 큰 문맥이면 먼저 인계·압축한다.
4. 인터페이스가 불명확하거나 공유 파일 충돌이 있으면 병렬 구현 전에 조정자가 설계를 마무리한다. Sol과 Astra를 순서대로 반드시 거칠 필요는 없다.
5. 실행 전 이유·역할·모델·병렬 수를 알린다. 작업자가 적용받은 실제 모델을 확인한다. 전환 도구가 없으면 변경했다고 말하지 않고 필요한 사용자 조작을 안내한다.
6. 작업자는 변경·검증·미해결 사항을 반환하고, 조정자는 합쳐진 결과와 경계의 동작을 확인한다. 변경 없는 검증은 재사용한다.

## 대표 유즈케이스

아래 Luna/max 사례는 앞선 우선순위에 따라 기본값을 적용할 수 있는 경우다. 프로젝트가 모델을 고정하면 작업자도 그 지정을 따르며, 사례 표 자체가 고정을 해제하지 않는다. 명시적 사용자 결정과 활성 quota 보호 규칙은 프로젝트 고정보다 우선한다.

| 상황 | 선택과 실행 | 완료 또는 재판단 기준 |
|---|---|---|
| 설계 완료 후 버튼 문구와 상태 조건 한 곳 수정 | 선택 위임 상태면 Luna/max. 짧은 작업이므로 서브에이전트 없이 현재 세션에서 수행 | 해당 상태의 실제 표시·동작 확인 |
| API 계약이 확정된 두 독립 컴포넌트 구현 | 조정자는 계약을 유지하고 Luna/max 작업자 2명에게 겹치지 않는 경로와 각각의 테스트를 배정 | 두 결과를 통합해 공통 API와 연결 검증. 공유 파일 수정이 필요하면 조정자에게 반환 |
| DB 마이그레이션·API·UI를 함께 바꾸며 데이터 의미가 불명확 | Sol/high로 의미·이행 순서·실패 영향을 검토하도록 제안. 계약 확정 전 병렬 구현 금지 | 계약 확정 뒤 독립적인 구현만 Luna/max에 위임. 필요한 데이터·권한이 없으면 상위 모델도 대신하지 못함 |
| 설계를 Astra로 끝냈고 구현은 길지만 순차적 | 모델 선택을 위임받았다면 인계 요약 후 Luna/max로 지원되는 전환 수행. Astra가 명시적으로 고정됐다면 유지하거나 전환 요청 | 실제 전환 확인 후 구현. 작업자를 띄워 고정 모델을 우회하지 않음 |
| 재현 가능한 국소 버그 | Luna/max로 재현·원인 가설·좁은 수정·회귀 확인 | 한 번 실패하면 증거부터 재검토. 같은 원인의 실패 반복 또는 새 결합 관계 발견 시 계획 수정 및 필요 모델 제안 |
| 여러 서비스의 드문 동시성·정합성 장애 | Astra/high를 제안하고 재현 조건·타임라인·좁힌 코드만 전달 | 검증 가능한 원인과 수정 계약 확보. 이후 명확한 구현은 Luna/max로 분리 가능 |
| Figma에서 지정된 카드의 여백·문구 변경 | Luna/max로 대상 노드와 연결 토큰만 조회·수정. 단일 작업자 | 시각 결과, 넘침, 정렬, 편집 가능 여부 확인 |
| Figma 디자인 시스템 전체를 재구성 | Sol/high로 토큰·변형·마이그레이션 경계를 먼저 설계하도록 제안 | 계약 후 서로 다른 화면을 Luna/max 작업자에게 배정. 공통 토큰은 한 명만 소유하고 병렬 수정 금지 |
| 브랜드 브리프에 맞는 광고 문안 5개 작성 | Luna/max 하나로 채널·타깃·CTA에 맞춰 생성 | 제품 주장 근거, 브랜드 말투, 길이 확인. 게시 권한과 별개 |
| 캠페인 조사·문안·시각 제작이 각각 상당한 작업 | Luna/max 조정. 작업자 1명은 출처 조사, 다른 1명은 확정 브리프에 따른 문안 등 독립 범위만 수행 | 조사로 메시지가 바뀔 가능성이 크면 먼저 조사. 최대 2명이지 항상 2명이 아님 |
| 시장 진입 전략의 가정이 충돌 | Sol/high 또는 불확실성이 특히 크면 Astra/high 제안 | 사실·가설·선택지·검증 계획 구분. 상위 모델을 근거 없는 수치의 대용으로 쓰지 않음 |
| 운영 배포·긴 테스트 대기 | 승인된 실행을 도구로 처리하고 로그는 파일에 보관. 단순 상태 조회를 위한 상위 모델·새 작업자 금지 | 실패 시 관련 부분만 조회, 성공한 같은 리비전의 검증 재사용 |

## 실행 전 안내 예시

> 설계와 API 계약이 확정됐습니다. 독립적인 두 화면은 Luna/max 작업자 2명에게 각각 맡기고, 공통 타입은 제가 관리하겠습니다. 각 작업자는 자기 화면과 검증 기준만 받아 전체 대화 복제를 피합니다. 병렬화는 시간을 줄이지만 사용량 절약을 보장하지 않습니다.

> 이번 구현은 한 파일의 짧은 변경이어서 현재 세션에서 처리하겠습니다. 모델 전환이나 작업자 생성 비용을 추가하지 않겠습니다.

> 현재 문맥이 16만 토큰입니다. 다음 배포 단계 전에 커밋·검증 결과·남은 일을 요약하겠습니다. 이 환경에서는 자동 압축을 실행할 수 없으므로, 요약을 바탕으로 압축 또는 새 세션 전환이 필요합니다.

## 작업자에게 전달할 계약

```text
목표: 사용자가 확인할 결과
소유 범위: 수정할 경로 또는 Figma 노드; 공유 영역 담당자
입력: 확정 인터페이스, 짧은 브리프, 필요한 자료 경로
제약: 사용자 결정, 기존 작업 보존, 승인 범위
검증: 관측 가능한 완료 조건과 필요한 검사
중단 조건: 계약 모호성, 경로 중복, 권한 부족, 반복되는 동일 원인 실패
반환: 변경 요약, 파일/노드, 검증 증거, 미해결 사항
```

조정자 포함 최대 3명이며 중첩 작업자도 센다. 상위 모델의 전체 문맥을 저렴한 작업자들에게 복제하는 방식은 피한다. 명시적 위임 금지와 provider 한도는 우선한다. 주간/5시간 한도가 80% 사용된 경우의 Luna/max 보호 규칙을 상위 모델 작업자로 우회하지 않는다.

## 확인 방법과 한계

실제 작업에서 입력/캐시/출력, 모델 호출 수, 품질·검증 성공, 재작업을 함께 비교한다. 모델 순위나 토큰 수만으로 절약을 확정하지 않는다. 모델 사용 가능 여부와 추론 옵션은 현재 호스트에서 확인한다. SessionStart는 이 정책을 전달할 뿐 실제 자동 라우터·과금 차단기가 아니다.
